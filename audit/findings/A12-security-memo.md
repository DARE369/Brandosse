# A12 — Security Audit Memo (P10s)

**Core question: if this launched publicly tomorrow, what gets breached?**

Answer: user data, immediately, at scale, with zero exploit sophistication required. The most severe finding (P10s-001/002) requires nothing more than a free signup and a browser dev console — no injection, no fuzzing, no privilege escalation needed to read it. That alone should block launch.

## What was actually tested (not inferred)

All RLS findings below are **behavioral**, not read from migration files. I authenticated as the real QA user via `POST {SUPABASE_URL}/auth/v1/token?grant_type=password` with the **anon** key (not service role), then issued PostgREST reads with that user's own JWT — exactly what a signed-up attacker could do from a browser. Service-role reads were used only to cross-check counts, never as the basis for an isolation claim.

## Findings, in order of exploitability

1. **P10s-001 / P10s-002 (CRITICAL, live-confirmed).** Any authenticated user can read `public.posts` (188 total rows, 7/20 sampled belonged to unrelated users) and `public.generations` (159 rows, 44/159 belonged to unrelated users, 39 of those with `organization_id = null`, i.e. pure personal data with zero org relationship to the reader) — full captions, AI prompts, timestamps, status. The migration-file text for both tables' policies (`auth.uid() = user_id OR can_admin_access_user(...)`, plus an org-scoped SELECT policy that provably cannot match a null `organization_id`) says this should be impossible. It isn't, live. Root cause unresolved — this needs someone with Supabase Studio access to run `SELECT * FROM pg_policies WHERE tablename IN ('posts','generations')` immediately, because migrations do not reflect the live policy set (this app has a documented history of exactly that drift). Tables checked and confirmed clean by the same method: `sessions`, `content_plans`, `personal_assets`, `video_clips`, `video_jobs`, `credit_transactions`, `user_credits`, `user_settings`, `content_library_items`, `studio_projects`, `brand_kit` — so this is not a project-wide `RLS OFF` situation, it's isolated to these two tables (or whatever they share that the others don't).

2. **P10s-006 (CRITICAL, code-confirmed, write-unverified).** `admin-list-posts` reimplements admin-role resolution locally instead of using the shared, correct helper (`_shared/org.ts:isSuperAdminUser`, which only trusts `admin_roles`). Its local version falls back to the user's own `profiles.role` column when no `admin_roles` row exists, and accepts a bare `"admin"` string. `profiles.role` is updatable by its own owner with no column restriction (`USING (auth.uid()=id) WITH CHECK (auth.uid()=id)`, no CHECK constraint, no column-level REVOKE). On paper: any user can `PATCH` their own `role` to `"admin"` and gain full moderation-panel read access to every user's posts and PII. I did not perform the write to confirm end-to-end — the brief is explicit about read-only, and this is the one place where confirming it fully requires a write. This needs a human to test directly, but the code path is unambiguous.

3. **P10s-007 (HIGH, code-confirmed).** The Zernio OAuth-account-linking callback (`app/api/auth/zernio/callback/route.js`) has zero CSRF/state protection and zero session check — it resolves *which user* to attach a connected social account to purely from a `profileId` query parameter, server-side, with no binding to whoever's browser is making the request. `OAUTH_STATE_SECRET`, which the prior audit memory flagged as "required but absent," turns out to be referenced **only in docs and CI — never in any actual code path**. It doesn't fail open or closed; it's simply not wired to anything. The code's own comment admits "there's no signed state to build."

4. **P10s-005 (CRITICAL, confirmed).** `docs/VIDEO_LAB_COMPLETE_GUIDE.md:538` has committed the real, still-active `VIDEO_WORKER_WEBHOOK_SECRET` value since the repo's first commit, in a **public** GitHub repo (`DARE369/Brandosse`, confirmed non-private via the GitHub API). It has never been rotated — `.env.local` has the identical value today. Currently low-exploitability only because the worker's configured URL is `localhost:8001`; a `railway.toml` in `video-worker/` shows a public-deployment path already exists for exactly this service. Separately: I could **not** reproduce the prior belief that real Groq/FAL/Pollination keys are in git history — a full-history pickaxe search found no such values, only `.env.example` placeholders. Treat that prior claim as unconfirmed/stale until someone checks it against whatever repo state produced it.

5. **P10s-003 (HIGH, architectural).** The live database is confirmed still shared with an unrelated tutoring product (`sessions` table carries `tutor_id`/`child_id`/etc., the QA account's own `profiles.role = 'parent'`). The specific bug this caused before (`is_tutor_for_session()` referencing a missing table, aborting all session reads) is fixed and verified live. But the architecture — one Postgres schema, two products, policies edited directly against the live DB outside of tracked migrations (per the baseline migration's own comments) — is the most plausible root cause for #1, though I could not confirm it without `pg_policies` access.

6. **P10s-004 (MEDIUM) / P10s-008 (MEDIUM).** `daily-analysis` is a service-role, all-users-writing cron function with no function-level auth check of any kind (contrast with `credit-monthly-reset`, which checks the bearer against the service-role key). Stripe webhook signature verification is solid, but credit-crediting idempotency is check-then-act with no DB unique constraint backing it — a genuine (if narrow) double-credit race.

## What I did not get to / lowest-confidence area

Root cause of #1 is the single most important open question — I have strong behavioral proof it happens and strong code-based proof it *shouldn't*, but not the specific live policy responsible. Someone with SQL Studio access should run `pg_policies` on `posts` and `generations` before anything else. I'd also want a live write-permitted follow-up to actually attempt the `profiles.role` self-escalation (#2) end-to-end rather than leaving it as a static-analysis call.

## Verdict

**Not safe to ship.** Any signed-up user can read a large fraction of every other user's private content today, with a normal browser and their own login — that alone is disqualifying regardless of what else is found. **Top must-fix: identify and drop whatever live policy is granting cross-user SELECT on `public.posts` and `public.generations` (P10s-001/002) — do this before anything else, including before the admin-role fix, because it's already being exploited by the mere existence of any second user account, no attacker intent required.**
