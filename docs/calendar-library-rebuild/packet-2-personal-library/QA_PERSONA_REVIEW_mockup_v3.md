## Flow A — Land on the Library cold with 12 assets, find the one worth posting today

**What every persona is trying to do:** scan a grid they've never seen mid-session and identify, without being taught how, which single asset is both finished and eligible to go out today.

**Traced from the mock's own state (`ASSETS` array + `renderVals()`):**
- The array literally holds 12 rows (`id: 1..12`), but `ids 11` and `12` carry `archived: true`. The default view (`source: 'all'`, `stateFilter: null`) filters through `active = ASSETS.filter(a => !a.archived)`, and every count on the page — the header's `{{totalCount}}` badge in the rail, and the `headline` string ("`X assets · Y ready to publish · Z never used`") — is computed from `active.length`, i.e. **10**, not 12. There is no visible number anywhere on first paint that says 12. A user has to already know to click the "Archived" state chip to discover the other two exist. For a persona landing "cold," as the task specifies, this means the premise of the task ("with 12 assets") is not a number this screen ever shows them.
- The toolbar's `<input>` (search) and both `<select>` elements (media type, sort) render with no `onChange`/`onInput` handler anywhere in the markup or in `renderVals()`'s returned object. Typing in the search box or changing "Sort by" does nothing — the visible list never re-filters or re-orders. Only the source chips (Uploads/Clips/Generated/Post records) and state chips (Never used/Archived/Trash) are wired (`onClick: () => this.setSource(key)` / `setStateFilter`).
- The "Sort by" dropdown's first, pre-selected option reads "Newest first," but the grid's actual order is just `ASSETS` array order, which is **not** date-sorted: id 1 (Sep 11) renders before id 3 and id 4 (both Sep 12, newer), which render before id 2 (Sep 10). A user relying on the label to mean what it says would be looking in the wrong place for the newest thing.
- What *does* work for "find the one worth posting": the per-card state tag (green "Ready," amber "No destination," blue "Tagging…," red "No file," grey "Post record") and the "fits N of M" note are genuinely computed per-asset from `publishState()` and render correctly for all 10 visible cards. A user willing to visually scan rather than search/sort would land correctly on one of the 4 "Ready" cards (ids 1, 2, 5, 7).

**Would it make sense without explanation:** the state tags and fit badges, yes — the labels are plain English and consistent. The search box and both dropdowns would not; nothing signals they're inert, and a first-time user has no reason to assume a rendered, focusable, apparently-functional search input does nothing.

**Verdict: CONCERN for every persona** — the fallback (visual scan) works, but the two tools purpose-built for exactly this task (search, sort) are decorative, and the page's own headline count doesn't match the number of assets actually in the workspace.

## Flow B — Understand "No file", "No destination", "Tagging…", "Post record"

**Traced state-by-state:**

- **No file / `blocked`** (asset 8, an upload with `gen: null`, explicitly annotated in the mock data as "Uploaded before the media-link repair" — this maps to a real, dated defect: `supabase/migrations/20260912090000_backfill_upload_generations.sql` backfills exactly this case, and the mock's inclusion of a pre-repair asset is accurate, not invented). Opening the drawer for this asset shows a dedicated red callout: *"This file can't reach a platform... Re-uploading rebuilds the link."* plus a "Re-upload" button. This is the one state that gets its own in-drawer explanation.
- **No destination / `nodest`** (assets 3, 6, 10 — images, fully tagged, with a valid file link, but neither connected account (YouTube, TikTok) accepts images). The *page-level* banner explains this correctly ("Only YouTube and TikTok are connected, and both take video only"). But opening the **drawer** for one of these three assets shows nothing — `tabIsDetails` only branches on `selected.isBlocked`, never on the nodest case. A user who filters past the page banner (e.g., arrives via the "Never used" chip, which doesn't show the banner) and opens the asset directly has no in-drawer explanation at all for why it's stuck.
- **Tagging… / `tagging`** (asset 4 only). The Library's own reference screen ("How content flows," reachable via the "How content flows →" chip) states in its own copy: *"The card shimmers until they land."* But the `.shimmer` CSS class this sentence is describing is defined once at the top of the stylesheet and **never applied to any element anywhere in the card markup** — grepped the full file, zero matches outside the definition and this one sentence. The actual "Tagging…" card just shows a static blue tag; there is no shimmer, skeleton, or any other animated in-progress indicator on the one asset actually in that state. This is the file contradicting its own documentation screen.
- **Post record / `record`** (asset 9, a text-only post). Correctly labeled and correctly gets a "View post" button instead of Publish. One rough edge: the card still renders its "fits" row with both platform badges crossed out (`fit--no`), with no note explaining why — for every other non-ready state the `fitNote` field explains itself ("no connected account takes images"), but `record` gets an empty `fitNote`, leaving two unexplained crossed-out icons sitting under a card that otherwise honestly says "Record of a post — no file."

**Verdict: CONCERN for every persona** — each state's *headline* copy is honest and non-fabricated (a real strength worth naming: nothing here invents a license alert or a fake campaign status the way a lesser mockup might), but the four states are not handled with equal care, and one of them is actively contradicted by the file's own reference documentation screen sitting one click away.

## Flow C — Publish a vertical video to YouTube, including the made-for-kids answer

**Walked with asset 1 ("Founder Q&A — the cold open"), state = `ready`.**

1. Card → Publish → sheet opens. `openPublish()` pre-selects only YouTube (`eligible.slice(0, 1)`), even though TikTok is equally eligible for this video — a persona in a hurry could easily not notice TikTok was never checked and publish to one platform believing they'd chosen both. Not a hard failure (the destination list is visibly there to check), but worth naming as a real "would they notice" risk for Sade specifically, given her stated profile (moving fast, one hand).
2. The caption textarea is pre-filled with `baseCaption`, a single hardcoded string ("The autumn restock is live — five pieces...") that is **identical for every asset in the file**, regardless of which one you opened. Publishing "Founder Q&A" would show a caption about an autumn restock. This is transparently a mockup shortcut (one demo string, not fabricated per-asset AI output), but it's also the first thing a reviewer sees inside the sheet, and it's wrong for the specific asset selected — worth being explicit about so nobody mistakes it for an actual caption-generation feature being demonstrated.
3. The character counter (`{{counterText}}`, e.g. "78 / 3000") is computed once from `baseCaption.length` and is **not wired to the textarea's actual contents** — there is no `onChange`/`onInput` on `#p-caption`. Typing a longer caption would never move the counter. For a flow whose entire purpose is "does this fit the platform's limit," a non-reactive counter is a meaningful gap, not a cosmetic one.
4. YouTube's requirement block asks for "Video title" (text) and "Is this made for kids?" (Yes/No, no default selected initially — wait, it does have a default: `madeForKids: 'no'` in initial state). The hint text — *"YouTube rejects the upload without an answer. There is no safe default, so we ask"* — is accurate to the real constraint (`youtube.service.ts:242-256`: `selfDeclaredMadeForKids` has no default and the function refuses to publish without it). This is the one piece of this flow that is both correct and load-bearing-accurate.
5. **What the flow never surfaces at all:** the real YouTube adapter forces every upload to `private`, permanently, until Google's compliance audit passes — `youtube.service.ts:30-35,142-173` states this explicitly, and `20260909160000_mark_tiktok_youtube_publishable.sql` records it as a known, current, unresolved platform-side restriction, not a hypothetical. The mockup's YouTube requirement block has no privacy/visibility field at all (unlike TikTok's, which at least shows one), and the confirmation toast after clicking "Publish now" reads only "Publishing to 1 account…" — nothing here, at any point in the flow, tells the user their video will not actually be visible to anyone but themselves.

**Would it make sense without explanation:** the mechanics (pick destination, write a title, answer the kids question, hit publish) are self-explanatory and match a familiar "compose" pattern. What would *not* make sense is discovering afterward — on YouTube itself, not in this app — that the video everyone can see is a private one nobody can watch, with zero warning anywhere in the flow that just told them "Publishing to 1 account…"

**Verdict: CONCERN, bordering on the most damaging single gap in this review** — see ranked list below.

## Flow D — Publish a still image, discover no account accepts it

**Walked with asset 6 ("Product hero — burnt orange"), state = `nodest`.**

- From the **card**: Publish button reads "Can't publish" (visually disabled: `opacity:.45; cursor:not-allowed`) but the `onClick` handler is still bound and still fires — clicking it calls `buildCard(a).onPublish`, which branches correctly to `st === 'nodest'` and shows: *"Connect LinkedIn to publish stills."* Specific, honest, actionable.
- From the **drawer footer**'s equivalent Publish button, the click instead goes through `openPublishFromDrawer`, a *separate* function: `selected && !selected.publishCls ? openPublish(id) : toast('This asset isn't publishable yet.')`. Because `publishCls` is a non-empty string (`'btn--disabled'`) for any non-ready/non-record asset, this always falls to the generic toast — **for every one of blocked, tagging, and nodest alike**, losing the specific, correctly-branched reason the card-level handler already knows how to give. A user who opens the drawer first (a completely normal thing to do — the drawer is the more detailed view) gets a strictly worse, vaguer answer than the one they'd have gotten by staying on the grid and clicking the card's own button.
- The visual "disabled" styling (`cursor:not-allowed`) on a button that is, in fact, still clickable and does something meaningful is a minor but real signal mismatch — it looks inert but isn't.

**Verdict: PASS, with one real inconsistency** — the *card's* explanation is exactly the kind of specific, non-punitive messaging Contributor Ada's stated need calls for ("never just a disabled button with no explanation"), which is worth crediting; the drawer regressing to a vaguer message for the identical action, on the identical asset, one click away, undercuts that.

## Flow E — Find out where an asset has been posted, and whether it ever was

- Drawer → "Where it's used" tab: assets with history (2, 6, 7, 9) show platform, timestamp, and a status pill (Published/Scheduled), each with an "Open" action. Assets with none (1, 3, 4, 5, 8, 10) get an honest empty state: *"Never published — This asset has been sitting here since {{date}}. Publishing it takes two clicks,"* with a primary "Publish it" button.
- That "Publish it" button is `openPublishFromDrawer` — the same function from Flow D. For an asset that's blocked or still tagging (e.g. asset 4, "Tagging…", or asset 8, "No file"), a user reading "Never published... Publishing it takes two clicks" and pressing the inviting primary-styled button gets bounced with "This asset isn't publishable yet" — a promise the copy just made ("two clicks") that the same click immediately contradicts, for assets in exactly those two states.
- "Open" on a used-in row fires `toast('Opening the {{platform}} post in Calendar')` — a stub, not a real link. Unlike the *previously reviewed* `mockup-gallery.html`, which used real cross-file `<a href>` navigation between the Library and Calendar galleries, this file makes no attempt at a real link anywhere for this action. That's a fidelity regression worth naming plainly (see the v3-vs-gallery note below), not a new defect being introduced here for the first time — the two mockups simply aren't at the same fidelity level for this particular interaction.
- As noted in Flow A: the 2 archived assets are invisible to any "has this ever been used" question asked from the default view — a user would need to already know to check "Archived" separately, and even then the Archived filter shows *only* archived assets, with no way to see "everything, archived or not, that touches this same underlying file" in one place (there's no cross-cutting search across archived + active, since search itself is inert).

**Verdict: PASS, with one meaningful gap** — the core question ("has this ever been posted") is answered honestly and clearly for the 10 visible assets; the archived-assets blind spot and the "Publish it" promise-then-bounce for non-ready assets are the two real rough edges.

## Flow F — Replace an asset with a better version without breaking already-published posts

- Drawer → Versions tab: for asset 6 (the only asset with `versions: 2` in the mock data), shows "v2 — current / colour-corrected" and "v1 / original upload," with the current one pilled. For every other asset, a single "v1 — current" row.
- The load-bearing guarantee — *"Replacing an asset supersedes the old one instead of overwriting it — posts already published keep the file they went out with"* — appears as **one sentence of static hint text**, never as something the interaction actually demonstrates. Clicking "Upload a replacement" calls `onNewVersion`, which is a toast (*"Pick a replacement file — the old version is kept"*) and nothing else: no file picker opens, no new version entry gets added to the list, no before/after state change of any kind. Given this guarantee exists specifically to prevent a real, serious failure mode (a live post's media silently changing under it, or breaking, after a creator replaces the source asset) — the exact category of thing Law 3 in this codebase's own engineering standards is written to catch — a reviewer cannot use this mockup to confirm the interaction actually *communicates* the guarantee holding. It can only confirm the guarantee is *asserted* in prose.

**Verdict: CONCERN** — not because the stated design is wrong (it is the right design, and matches the "versions supersede" language the packet's own audit trail already established as real for `personal_assets`), but because the one flow explicitly built to prove out a data-safety guarantee doesn't do anything interactive to prove it.

## Flow G — "I have a long video on YouTube" → "a clip from it is live on TikTok"

This is the flow the task specifically asks me to name every screen crossed and every place the trail goes cold, so I'll do that literally.

**Screen 1 — finding/clipping the long video.** The rail has a "Video Clips" nav item and the "Add content" menu has "Clip a long video / Paste a URL — we cut it into shorts." Both are stubs: `noopNav` fires the toast *"That screen is out of scope for this mockup"* (honest, in-context disclosure — credit where due, it doesn't pretend to work), and `onAddClip` fires *"Opening Video Clips — paste a URL"* and nothing else opens. **The trail goes cold here, immediately, for the entire front half of this flow** — there is no screen in this file for pasting a URL, selecting a 41-second segment out of a longer stream, previewing it, or confirming "save this clip to my Library." Everything from "long video" to "clip exists as a Library asset" happens entirely off-screen, represented only by two pre-seeded rows in the mock data (`id 1`, `id 2`, both `source: 'clip'` with a `from`/`at` field showing where they were cut from).

**Screen 2 — the Library, once the clip already exists.** This is the only part of the journey the file actually models. The clip card (e.g. id 1) correctly shows its source badge ("Clip"), its provenance line ("Clipped from 'Founder AMA — full stream' · 12:04–12:45"), and its Ready state. This part works and is legible.

**Screen 3 — the publish sheet, choosing TikTok.** Selecting TikTok surfaces the one platform-specific field: "Who can see it," a segmented Only-me/Public control, whose hint reads *"Until the app passes TikTok's content audit, only 'Only me' is permitted."* That hint is accurate — `_shared/tiktok.service.ts:25-30` states the real API returns `403 unaudited_client_can_only_post_to_private_accounts` unless `privacy_level = SELF_ONLY` and the destination account is private, and the same fact is recorded in `20260909160000_mark_tiktok_youtube_publishable.sql`. **But the control's initial state (`privacy: 'public'`) defaults to the option the hint just said isn't permitted, and nothing stops it from being selected or submitted.** A user who reads the hint, then clicks "Publish now" anyway (or simply never toggles away from the pre-selected "Public"), gets the same undifferentiated *"Publishing to 1 account…"* toast as any successful publish — **this is the second place the trail goes cold**: the UI cannot distinguish, and does not attempt to distinguish, between a publish that will actually succeed and one that the real TikTok API is guaranteed to reject with a specific, already-known error.

**Screen 4 — confirmation.** There isn't one, beyond the single toast. TikTok's real publish path is explicitly asynchronous — `tiktok.service.ts`'s own header comment states this is deliberate, because *"returning success at step 2 would report posts as published that TikTok later rejected"* — and the real adapter polls a status endpoint up to 20 times before it will call anything published. The mockup's instantaneous, no-follow-up "Publishing to 1 account…" toast is the exact shape of claim the real backend was specifically written to avoid making.

**Verdict: FAIL** — not because the disclosed-out-of-scope front half is a defect (it's an honest, in-context "not modeled here," which is the right way to leave something out), but because the flow the task actually asks to be walked cannot be completed end-to-end inside this file, and the one part of it that *is* modeled (the TikTok publish) defaults to, and does not block, a setting that the real backend is documented to reject outright.

## v3 vs. the already-reviewed gallery — one thing the human approver needs to see

The earlier review of `mockup-gallery.html` flagged one open concern as "the single most important thing for the human approval gate": the Schedule hand-off to Quick Post didn't carry the selected asset through, even though it used a *real* cross-file link and landed on the *correct* anchor. In `library-v3.dc.html`, that same hand-off (`onSchedule`, both card- and drawer-level) is now **only** a toast — `"Opening Calendar with '{{title}}' attached"` — with no link, no anchor, no cross-file navigation attempted at all. If v3 is meant to supersede the gallery mockup, this is a fidelity regression on the packet's own previously-named highest-value flow, not a fix to it: the earlier version could at least be evaluated end-to-end and found wanting; this version cannot be evaluated end-to-end at all.

## Ranked list of most damaging gaps

1. **YouTube publish never discloses the forced-private constraint.** A user completes Flow C believing they've published a public video; the real adapter (`youtube.service.ts:30-35`) forces every upload private until a compliance audit passes, permanently, unappealably. Nothing in the sheet, the requirement fields, or the confirmation toast says so. **What a real user does next:** checks their YouTube channel later, finds the video isn't visible to anyone, assumes the app is broken or that publishing silently failed, and either retries (no effect) or contacts support — the actual cause (a platform-side restriction, not a bug) is undiscoverable from inside the product.

2. **TikTok publish defaults to, and permits selecting, a privacy level the real backend is documented to reject.** The hint text correctly states only "Only me" is currently allowed; the control still defaults to "Public" and does not block submission. **What a real user does next:** hits "Publish now," gets a generic-looking success toast, and only discovers the post never actually went out (or went out privately/differently than expected) when they go look for it on TikTok — by which point the connection between "I clicked publish" and "it didn't work" is already broken, because the app told them it worked.

3. **The one flow built to prove Flow G end-to-end cannot be walked end-to-end.** The front half (source video → clip) is entirely off-screen; the trail cannot be followed from "I have a long video" to "a clip is live," which is the exact promise this flow's own name makes.

4. **Metadata edits in the drawer (Title, Description, Alt text, Tags) have no Save control at all.** Unlike the earlier gallery mockup (which at least had a Save button, even if unconfirmed), this version's drawer footer only offers Schedule / Publish / Duplicate / Archive / Move to trash — there is no button anywhere to commit an edited title or alt text. **What a real user does next:** types a correction, closes the drawer (the only exit), and has no way to know whether anything they typed was kept.

5. **Lifecycle actions (Archive, Move to trash, Duplicate, "Upload a replacement") never change anything visible.** Each is a toast claiming an outcome ("Archived — still searchable, hidden from the grid" / "Moved to trash — recoverable for 30 days") that the underlying state never enacts — the asset stays exactly where it was, in the exact same filter, after the toast fires. **What a real user does next:** trusts the toast, believes the asset is gone/archived, and is confused or alarmed to see it still sitting in the main grid the next time they look.

6. **Search and both filter dropdowns are inert.** For a screen whose entire Flow A job is "help me find one thing among several," the two tools most obviously built for that are decorative.

7. **The character counter in the publish sheet doesn't track what's actually typed.** A caption-length problem (the one thing platform character limits actually punish) would go undetected until the real platform rejects it.

8. **The drawer's Publish button gives a strictly worse explanation than the card's Publish button for the identical asset, identical reason.** Undermines the file's own stated principle ("the card says so before you click, not fourteen seconds after") by not carrying that principle to the second place the same action lives.

9. **The Flow reference screen asserts a behavior ("the card shimmers") that no card in the file ever performs.** Self-contradiction inside the same artifact — a reviewer who reads that screen first and then checks the actual "Tagging…" card would reasonably conclude the shimmer was cut and nobody updated the documentation screen to match.

10. **"12 assets" is never a number this screen shows a first-time user.** Archived assets are excluded from every visible count by default; discovering there are 12, not 10, requires already knowing to check a filter most people would have no reason to click.
