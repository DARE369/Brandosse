### YouTube — root cause found and fixed

Traced `updatePostProduction` to `src/components/Generate/PostProductionPanel.jsx:334`,
a store action fired from a `useEffect` keyed on `[youtubeSettings]`. The
`youtubeSettings` state comes from `YouTubeOptionsPanel`'s `onChange`, wired at
`PostProductionPanel.jsx:1293-1298` as an **inline arrow function** — a fresh
identity every render, same shape at all three call sites
(`Generate/PostProductionPanel.jsx`, `Studio/PostProductionPanel.jsx:254-256`,
and previously `QuickPostComposer.jsx` before it was fixed there directly).

`YouTubeOptionsPanel.jsx:120-129` (before this pass) listed `onChange` and
`onValidityChange` in their own effects' dependency arrays:

```
useEffect(() => { if (isValid) onChange?.(settings); }, [isValid, settings, onChange]);
useEffect(() => { onValidityChange?.(isValid); }, [isValid, onValidityChange]);
```

Loop: effect fires → parent's inline `onChange` runs → `setYouTubeSettings`
→ re-render → new inline `onChange` identity → effect fires again. React
caught it and threw before first paint — the global error boundary, exactly
like the video-jobs outage documented in the 2026-09-23 journal, different
root cause (loop, not `ReferenceError`).

**Not a new defect.** `TikTokOptionsPanel.jsx:161-175` already hit this exact
shape once and fixed it by excluding `onChange`/`onValidityChange` from its
effect's deps, with a comment saying why. `QuickPostComposer.jsx:276-291` also
already documents the same failure in a long comment and works around it with
a per-platform ref-cached handler. Neither fix reached `YouTubeOptionsPanel.jsx`
itself, which is why it broke at two more call sites.

**Fix.** `src/components/Publishing/YouTubeOptionsPanel.jsx:120-133` — mirrored
TikTokOptionsPanel's fix: removed `onChange`/`onValidityChange` from both
effects' dependency arrays, with `eslint-disable-next-line
react-hooks/exhaustive-deps` and a comment. This fixes all three call sites at
once, including the previously-unpatched Studio panel, rather than requiring
every caller to remember the ref-cached workaround.

### Guard — new, proven both ways

**Built `scripts/check-effect-callback-prop-deps.cjs`.** Walks the TypeScript
AST (same approach as `check-undefined-identifiers.cjs`) over every
`useEffect`/`useLayoutEffect` in `src/**/*.jsx` and `app/**/*.jsx`: flags any
call whose dependency array contains an identifier named like a callback prop
(`/^on[A-Z]/`) that is also invoked at the effect's own top level (not inside
a nested function the effect registers, e.g. an event handler — that pattern
is legitimate and already used correctly elsewhere, e.g.
`CalendarCommandBar.jsx`).

- **On the current (fixed) tree** — exit 0, 358 component files, clean.
- **On the pre-fix committed version** (restored from `git show HEAD:...`,
  guard run, then the fix restored) — **exit 1**, naming
  `YouTubeOptionsPanel.jsx:120` (`onChange`) and `:127` (`onValidityChange`)
  exactly.

Registered as `npm run check:effect-callback-prop-deps` (`package.json`) and
as a CI step in `.github/workflows/ci.yml`, after `check-xhr-stall-guard`.
Re-ran `check-undefined-identifiers` after — still clean at 548 files.

Modal showed only *"edge function returned a non-2xx status code"* — Supabase
JS's own `FunctionsHttpError.message`, not `publish-post`'s real reason.
Traced to `mockPublishService.js:4` (before this pass):

```
const message = error?.context?.json?.error || error?.message || ...
```

`error.context` is the raw fetch `Response` object `FunctionsHttpError` was
thrown with (confirmed against `@supabase/functions-js` source directly:
`types.ts:91`, `FunctionsClient.ts:297`) — `.json` on a `Response` is a
**method**, not a value. Reading `.error` off that function is always
`undefined`, so this discarded the real backend message on **every** genuine
non-2xx from `publish-post`, for any platform, on the manual "Post now"/
"Retry now" path specifically (`mockPublishService.js`'s own header comment
names this as the function actually used for that button, despite the
filename). TikTok/YouTube showed specific text in the same batch only because
those two failures were soft 200-with-`failureReason` returns — an unrelated,
unaffected path.

**Fixed** (`src/services/platforms/mockPublishService.js`): replaced the ad
hoc body read with `edgeFunctionClient.js`'s already-correct
`normalizeEdgeFunctionError` (awaits `context.json()` properly, `.clone()`-
guarded `.text()` fallback) — the same helper six other callers in this repo
already use successfully.

**Guarded.** New `scripts/test/publish-error-message.test.mjs`: behavioral
checks against `normalizeEdgeFunctionError` with a synthetic
`FunctionsHttpError` built the same way the real SDK builds one (a real
`Response` object as `context`), plus a static check that
`mockPublishService.js` actually imports and awaits it. Proven both ways —
restored the pre-fix committed file (`git show HEAD:...`), ran the test:
